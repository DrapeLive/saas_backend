# Drape SaaS API — Developer Documentation

This document describes the HTTP API served by the Drape SaaS backend, how the
generated OpenAPI schema is produced, and the conventions it follows.

## Live schema endpoints

| Route          | Purpose                             |
| -------------- | ----------------------------------- |
| `/api/schema/` | Raw OpenAPI 3.0.3 schema (YAML)     |
| `/api/docs/`   | Swagger UI (interactive)            |
| `/api/redoc/`  | ReDoc (human-readable reference)    |
| `/api/schema/` | `?format=json` for the JSON variant |

The schema is generated by **drf-spectacular**. Regenerate it locally with:

```bash
python manage.py spectacular --file schema.yml --validate
```

`--validate` verifies the output is a structurally valid OpenAPI 3.0 document.
A CI workflow (`.github/workflows/openapi.yml`) re-generates the schema on every
push/PR and fails if the committed `schema.yml` has drifted.

## Authentication

All non-auth endpoints require a bearer token:

```
Authorization: Bearer <access_token>
```

- Obtain a token via `POST /api/auth/login/` (`{"email", "password"}`).
- Refresh via `POST /api/auth/refresh/` (`{"refresh"}`).
- The OpenAPI schema declares the `jwtAuth` security scheme, so interface
  generators can wire the header automatically.

### Multi-company agents

Agents can belong to several companies via `AgentCompanyMembership`. Their JWT
may carry no `company_id` claim. For any company-scoped request from an agent
token, pass the target company explicitly:

```
X-Company-Id: <uuid>
```

The header is documented per-endpoint where honoured (e.g. agent switch-company,
agent performance, my-company endpoints).

## Company & data scoping

Except for Super-Admin endpoints, every resource is scoped to the authenticated
user's company. `retrieve`/`update`/`delete` requests for a record outside the
current company return a flat `404 {"detail": "Not found."}` rather than a 403,
so callers cannot probe for cross-company existence.

Role-based access:

- **Super Admin** (`superadmin`) — platform onboarding, plan/company lifecycle.
- **Admin** (`admin`) — full company management.
- **Sub Admin** (`sub_admin`) — admin minus a few sensitive actions.
- **Agent** (`agent`) — read/create scoped to own records; several endpoints
  are admin/sub-admin only.

## Error envelope

The global exception handler flattens every error to:

```json
{ "detail": "Human-readable error message." }
```

For DRF serializer validation errors, the first field error message is promoted
into `detail`. Status codes used across the API:

| Code | Meaning                                                     |
| ---- | ----------------------------------------------------------- |
| 400  | Bad request / validation failure                            |
| 401  | Missing, invalid or expired token                           |
| 403  | Authenticated but not permitted                             |
| 404  | Not found (including cross-company lookups)                 |
| 409  | Business-rule conflict (e.g. duplicate, invalid transition) |
| 429  | Rate limit exceeded                                         |

## Tags

The 21 top-level tags group the schema by domain:

`Authentication`, `Accounts`, `Companies`, `Agents`, `Customers`, `Products`,
`Categories`, `Size Charts`, `Stock`, `Orders`, `Dispatch`, `Invoices`,
`Payments`, `Plans`, `Subscriptions`, `Commissions`, `Notifications`,
`Audit Logs`, `Tally Integration`, `Admin`, `Super Admin`.

## Operation ID convention

`operationId`s use project-wide camelCase for client code generation:

- `listProducts`, `getOrder`, `createOrder`, `updateOrderStatus`,
  `approveOrder`, `markDispatchDelivered`, `getMySubscription`,
  `listCustomers`, `syncOfflineOrders`, ...

POST/PATCH actions that mutate a single resource follow `<verb><Resource>`.
List endpoints use `list<Resource>`; detail `get<Resource>`.

## Enum schemas

Shared enum schemas are emitted once under `components.schemas` with stable,
domain names (`OrderStatusEnum`, `InvoiceStatusEnum`, `CustomerSegmentEnum`, …)
via `SPECTACULAR_SETTINGS["ENUM_NAME_OVERRIDES"]`. This keeps the schema compact
and codegen-friendly — change `config/settings.py` if a new enum needs a stable
name.

## Response shapes

- List endpoints that page return the default DRF page envelope
  (`count`, `next`, `previous`, `results`). Products inventory returns a
  richer envelope with `summary` and `filters`.
- Mutation confirmations return `{"detail": "message"}` unless a full resource
  or a dedicated response serializer is documented.

## Writing schema docs for a new endpoint

1. Give every `GenericViewSet` a `serializer_class` or `get_serializer_class()`.
2. Annotate with `@extend_schema_view(...)` per method:
    - `tags`, `summary`, `description`, `parameters`, `request`, `responses`.
3. Use the shared helpers from `apps/core/openapi.py` for the standard error
   responses (`RESPONSE_400`, `RESPONSE_401`, `RESPONSE_403`, `RESPONSE_404`,
   `RESPONSE_409`) and `COMPANY_HEADER_PARAM`.
4. Custom actions that are URL-mapped via `as_view({...})` must carry a DRF
   `@action` decorator, otherwise drf-spectacular ignores their docs.
5. Type `SerializerMethodField`s with `@extend_schema_field(...)`.
