SUPERADMIN COMPANY AND SUBSCRIPTION API
=======================================

Authentication
--------------
Send a JWT access token in every request:
Authorization: Bearer <access-token>

Every endpoint in this document requires an authenticated user whose role is
"superadmin". Tenant admins cannot access these management endpoints.

Company management
------------------
GET /api/super-admin/companies
    List companies with company status, plan, subscription status and period
    dates.

GET /api/super-admin/companies/{company_id}
    Get complete company details, settings and subscription.

PATCH /api/super-admin/companies/{company_id}
    Update company profile and platform integration fields. The slug and
    lifecycle status are read-only here.

DELETE /api/super-admin/companies/{company_id}
    Soft-delete a company. Active companies must be cancelled or expired first.

POST /api/super-admin/companies/{company_id}/status
    Set a lifecycle status. JSON body:
    {"status": "pending|trial|active|grace|expired|suspended",
     "reason": "optional explanation"}
    When a subscription exists, trial/active/grace/expired/suspended are applied
    to the subscription and the company is synchronized atomically.

POST /api/super-admin/companies/{company_id}/suspend
    Suspend the company and its subscription, if present.

POST /api/super-admin/companies/{company_id}/activate
    Reactivate the company and its subscription, if present, with a fresh
    billing period.

POST /api/super-admin/companies/{company_id}/extend-trial
    Extend a trial by 1-90 days. JSON body:
    {"days": 14, "reason": "optional explanation"}

POST /api/super-admin/companies/{company_id}/impersonate
    Issue a short-lived access token for the company's first admin. The action
    is recorded in the audit log.

Plan management
---------------
GET /api/plans/
POST /api/plans/
GET /api/plans/{plan_id}/
PATCH /api/plans/{plan_id}/
POST /api/plans/{plan_id}/toggle-active/
POST /api/plans/seed-defaults/

Plans are global. A plan cannot be deactivated while trial or active
subscriptions use it. Subscription creation and plan changes reject inactive
plans.

Subscription management
-----------------------
GET /api/subscriptions/?status={status}&tier={tier}
    List subscriptions. Supported statuses: trial, active, grace, expired,
    cancelled, suspended.

POST /api/subscriptions/
    Create the one subscription owned by a company. JSON body:
    {"company_id": "...", "plan_id": "...", "billing_cycle": "trial|monthly|yearly"}
    A company cannot receive a second subscription. Trial billing requires a
    plan with trial_days greater than zero.

GET /api/subscriptions/{subscription_id}/
GET /api/subscriptions/{subscription_id}/events/
GET /api/subscriptions/{subscription_id}/usage/

POST /api/subscriptions/{subscription_id}/upgrade/
    Change plan or billing cycle. JSON body:
    {"plan_id": "...", "billing_cycle": "monthly|yearly|trial",
     "discount_pct": 0, "notes": "optional"}
    The price is recalculated, entitlements are snapshotted to company settings,
    the company becomes active, and an audit event is created.

POST /api/subscriptions/{subscription_id}/extend/
    Extend by 1-365 days. JSON body:
    {"extend_days": 30, "notes": "optional"}
    Trial dates and company status are synchronized.

POST /api/subscriptions/{subscription_id}/cancel/
    Immediately cancel the subscription and expire its company. Optional JSON:
    {"notes": "optional"}

POST /api/subscriptions/{subscription_id}/reactivate/
    Reactivate a cancelled, expired, suspended or grace subscription with a
    fresh billing period and synchronized company status.

Automatic lifecycle
-------------------
Celery beat runs subscription expiry processing hourly. When a trial or active
period ends, it becomes grace for seven days. When grace ends, it becomes
expired. Each transition updates the company and creates an immutable event.

Subscription payments
---------------------
All subscription payment endpoints below are superadmin-only. They are
separate from tenant invoice/customer payments.

GET /api/subscription-payments/?status={status}&subscription_id={id}
    List payment records. Statuses: pending, succeeded, failed, refunded.

POST /api/subscription-payments/
    Create a pending payment record. JSON body:
    {"subscription": "...", "amount": 1999.00, "currency": "INR",
     "payment_method": "upi", "provider": "manual|razorpay|stripe",
     "provider_payment_id": "optional-provider-id",
     "idempotency_key": "unique-client-key", "notes": "optional"}
    The idempotency key prevents duplicate payment records.

GET /api/subscription-payments/{payment_id}/
    Get payment details.

POST /api/subscription-payments/{payment_id}/confirm/
    Mark a pending payment as succeeded. This records paid_at, renews the
    subscription for its monthly/yearly cycle, sets the company active,
    refreshes plan entitlements, and creates a renewed subscription event.
    Repeating this request is idempotent.

POST /api/subscription-payments/{payment_id}/fail/
    Mark a pending payment as failed. Does not change subscription access.
    Optional JSON body: {"notes": "reason"}

POST /api/subscription-payments/{payment_id}/refund/
    Mark a succeeded payment as refunded. This does not silently revoke an
    already-granted subscription period; suspend/cancel the subscription
    explicitly when the refund requires access removal.
    Optional JSON body: {"notes": "reason"}

Payment flow
------------
1. Create a subscription payment as pending.
2. Send the payment to the configured provider, if applicable.
3. Confirm only after the provider reports success.
4. The confirm endpoint renews the subscription and company automatically.
5. Failed payments do not renew access. Celery continues moving unpaid
   subscriptions from active/trial to seven-day grace and then expired.

Recommended dashboard flow
--------------------------
1. Seed or create plans.
2. List pending/trial companies.
3. Create one subscription for each approved company.
4. Use subscription upgrade, extend, cancel and reactivate actions for billing
   operations; do not edit company.status directly for subscribed companies.
5. Poll company/subscription list endpoints for status, plan and renewal dates.
6. Display events and usage from the subscription detail endpoints.
